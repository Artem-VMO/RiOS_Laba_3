# Лабораторная работа №3. Проектирование системы автоматизированного КПП
## 1. Описание предметной области, акторы, пользовательские сценарии

## Описание системы:
Система автоматизирует въезд и выезд на платную парковку крупного предприятия, жилого массива или иного объекта. Сотрудники или арендаторы могут приобретать временные пропуска на парковку. На въезде установлена камера с ИИ (Computer Vision), которая распознает номерной знак. Если для автомобиля есть активный пропуск, система дает команду шлагбауму открыться. Если нет — шлагбаум остается закрытым, а система фиксирует попытку несанкционированного въезда.

## Акторы:

- **Водитель (Клиент)** — покупает пропуск, въезжает/выезжает.
- **Администратор парковки** — управляет тарифами, блокирует нарушителей, смотрит отчеты.

### Ключевые пользовательские сценарии:

- *Как Водитель, я хочу купить месячный пропуск, чтобы парковаться без ограничений.*
- *Как Водитель, я хочу, чтобы шлагбаум открывался автоматически при подъезде, чтобы не стоять в очереди.*
- *Как Администратор, я хочу видеть историю въездов, чтобы разбирать спорные ситуации.*
- *Как Администратор, я хочу, чтобы камера передавала распознанный номер в систему, чтобы получать решение «открыть/не открывать».*

## 2. Доменные события и ограниченные контексты с глоссариями

### Доменные события (Event Storming):

- **ПропускЗаказан**

- **ОплатаПрошла (ПропускАктивирован)**

- **НомерРаспознан (Камерой)**

- **ВъездРазрешен (Шлагбаум открыт)**

- **ВъездЗапрещен (Нарушитель)**

- **АвтомобильВыехал**

### Ограниченные контексты (Bounded Contexts) и глоссарии:

**Биллинг (Billing):**

- Пропуск — право доступа.
- Счет — документ на оплату.
- Тариф — стоимость пропуска.

**Контроль доступа (Access Control):**

- Автомобиль — транспортное средство (идентифицируется по номеру).
- Зона — парковочное пространство.
- Событие въезда — факт пересечения границы.

**Мониторинг (Gate):**

- Распознанный номер — строка символов от ИИ.
- Шлагбаум — физическое устройство.
- Команда управления — сигнал на открытие/закрытие.

**Аналитика (Reporting):**

- Загруженность — процент занятых мест.
- Нарушитель — автомобиль без пропуска.

## 3. Карточки сервисов и отвергнутые варианты разбиения
В соответствии с требованиями выделим 5 бизнес-сервисов. API Gateway и Keycloak считаются инфраструктурой.

### 3.1. pass-service (Сервис пропусков)
| Поле | Что указать |
|---|------------------------|
|  Название    |     pass-service        |
| Ответственность |Управление жизненным циклом пропусков (создание, активация после оплаты, аннулирование). |
|    Владеет данными  |    Pass (ID, Номер авто, Срок действия, Статус).         |
|   Предоставляет   |     REST API для проверки валидности пропуска.        |
|    Зависит от  |       Слушает событие payment.completed от payment-service.      |
|   Нефункциональные требования   |    Высокая доступность (99.9%), так как от него зависит въезд.         |
|  Обоснование границы    |   Это ядро бизнеса (право доступа). Отделен от платежей, так как пропуск можно выдать вручную администратором, без оплаты.         |


### 3.2. parking-service (Сервис учета мест)
| Поле | Что указать |
|---|------------------------|
|  Название    |     parking-service        |
| Ответственность |Учет свободных мест на парковке, контроль вместимости. |
|    Владеет данными  |   ParkingZone (Общее кол-во мест, Занято).        |
|   Предоставляет   |    gRPC API для резервирования/освобождения места.        |
|    Зависит от  |      Получает команды от access-service при въезде/выезде.      |
|   Нефункциональные требования   |    Сверхнизкая задержка (Low Latency).    |
|  Обоснование границы    |   Логика подсчета мест отличается от логики прав доступа. Требует блокировок (Redis) для предотвращения двойного занятия. |


### 3.3. access-service (Сервис контроля доступа / Въезда)
| Поле | Что указать |
|---|------------------------|
|   Название   |   access-service          |
| Ответственность     |   Принятие решения о въезде. Является оркестратором для шлагбаума.          |
|  Владеет данными    |    AccessEvent (Лог въездов/выездов, время, номер).         |
|  Предоставляет    | REST API для приема номера от камеры, публикует события vehicle.entered.            |
|   Зависит от   | Синхронно вызывает pass-service (проверить пропуск) и parking-service (забронировать место).            |
|  Нефункциональные требования    | Критичность к задержкам (время реакции < 1 сек).             |
|  Обоснование границы    | Здесь сосредоточена сложная логика проверок (пропуск + наличие мест + черный список). Отделен от шлагбаума.            |


### 3.4. payment-service (Сервис платежей)
| Поле                | Что указать |
|---------------------|------------------------|
| Название                    |    payment-service         |
| Ответственность     |Интеграция с банком, проведение оплат за пропуска, возвраты.             |
| Владеет данными     |Payment (Сумма, Статус, ID транзакции).             |
| Предоставляет       |API для инициации платежа, слушает коллбэки от банка.             |
| Зависит от          | Публикует событие payment.completed.            |
| Нефункциональные требования |Высокая надежность, строгий аудит.             |
| Обоснование границы |Изолирует работу с деньгами и внешними банковскими API. Ошибка в биллинге не должна блокировать работу шлагбаума.             |


### 3.5. iot-gateway-service (Сервис управления оборудованием)
| Поле | Что указать |
|---|------------------------|
|Название      |  iot-gateway-service           |
| Ответственность     |Прямое взаимодействие с физическим оборудованием (камеры, шлагбаумы) по протоколу MQTT или HTTP.             |
|  Владеет данными    |   DeviceStatus (Состояние устройства, IP).           |
|  Предоставляет    |Слушает команды gate.open, отправляет события о статусе оборудования.             |
|   Зависит от   | Получает команды от access-service.            |
|  Обоснование границы    | Аппаратная часть может зависать. Если шлагбаум потерял связь, это не должно ронять сервис проверки пропусков.            |


### Отвергнутые варианты разбиения:
- Рассматривали создание отдельных camera-service и barrier-service. Отказались, так как они выполняют чисто техническую функцию и работают в паре с одним физическим объектом. Лучше объединить их в один iot-gateway-service.

## 4. Таблица выбранного ПО с обоснованием
| Компонент | Кто использует | Обоснование |
|-----------|----------------|-------------|
| PostgreSQL | pass-service, payment-service | Транзакционная целостность при покупке и активации пропусков, связи между клиентом и пропуском. |
| MongoDB | access-service | Логи въездов (AccessEvent) — это большой поток событий с разной структурой (разные камеры могут присылать разный JSON). Гибкая схема. |
| Redis | parking-service | Хранение счетчиков свободных мест и механизм распределенных блокировок (TTL на удержание места, пока шлагбаум открывается). |
| RabbitMQ | access, payment, pass, iot | Надежная доставка команд на открытие шлагбаума и событий об оплате. Поддерживает сложную маршрутизацию. |
| Nginx (API GW) | Клиентский вход | Маршрутизация, проверка JWT (токены от Keycloak), защита от DDoS на эндпоинты оплаты. |
| Keycloak | Gateway | OAuth 2.0 / OpenID Connect. Аутентификация водителей и администраторов. |
| MinIO (S3) | access-service | Сохранение фотографий с камеры в момент въезда для подтверждения (доказательная база). |

## Таблица взаимодействий

| № | Инициатор → Получатель | Тип | Эндпоинт или событие | Назначение |
|---|------------------------|-----|----------------------|------------|
| 1 | Камера → iot-gateway | sync (REST) | POST /api/v1/camera/events | Передача распознанного номера |
| 2 | iot-gateway → access-service | sync (gRPC) | CheckAccess | Запрос на проверку доступа |
| 3 | access-service → pass-service | sync (REST) | GET /internal/v1/passes/check?plate={plate} | Проверить наличие активного пропуска |
| 4 | access-service → parking-service | sync (gRPC) | ReserveSpot | Забронировать место за автомобилем |
| 5 | access-service → RabbitMQ | async | gate.open.command | Команда на открытие шлагбаума |
| 6 | payment-service → RabbitMQ | async | payment.completed | Событие успешной оплаты (pass активируется) |

## Бизнес-сценарий со сквозной согласованностью (Saga)
### Сценарий: Въезд автомобиля на парковку (Успешный путь)
- Камера видит номер "|A001AA|161|" и отправляет его в iot-gateway.
- iot-gateway вызывает access-service.
- access-service синхронно проверяет пропуск в pass-service (ОК).
- access-service синхронно резервирует место в parking-service (ОК, место заблокировано на n времени).
- access-service публикует команду gate.open.command в RabbitMQ.
- iot-gateway получает команду, открывает физический шлагбаум (отправляет сигнал контроллеру) и публикует событие gate.opened.
- access-service получает gate.opened и сохраняет лог въезда в MongoDB.

### Действия при сбое (Компенсации):
- Сбой на шаге 3 (пропуск не найден): access-service возвращает ошибку, публикует событие access.denied, iot-gateway зажигает красный свет.
- Сбой на шаге 4 (мест нет): access-service возвращает ошибку, iot-gateway не открывает шлагбаум.
- Сбой на шаге 5 (RabbitMQ упал): access-service использует паттерн Transactional Outbox (сохраняет команду в свою БД и фоновый процесс ретраит отправку).
- Сбой на шаге 6 (шлагбаум не открылся): parking-service по таймауту (30 сек) снимает блокировку (компенсация).
